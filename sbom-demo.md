# SBOM Demo Talking Points

## What to show
Open `sbom/sbom.cdx.json` or the ASPM SBOM view and start from the application, not the CVE list.

Explain that an SBOM is the software ingredient list for a release. It records components and versions so X can answer:

- What third-party/open-source components are inside this application?
- Which exact versions were shipped?
- Which products are affected when a new CVE is disclosed?
- Which component should engineering upgrade?
- Can X provide software-component evidence with its security clearance?

## Demo flow

`Application -> SBOM -> Component -> Version -> SCA vulnerability -> Recommended upgrade -> ASPM application risk -> X security clearance`

## Important distinction

- **SBOM** = what software components are present.
- **SCA** = which of those components have known security or license risk.
- **ASPM** = correlates those findings with the application, source repository, ownership, release context, SLA, and remediation workflow.

## Recommended customer statement

“X remains the security-clearance authority. ASPM continuously generates and correlates the evidence that supports that decision, including software composition, code risk, exposed secrets, and infrastructure risk.”

## Regenerating the SBOM

With Syft:

```bash
syft dir:. -o cyclonedx-json=sbom/sbom.cdx.json
```

Or use:

```bash
./scripts/generate-sbom.sh
```

The committed `sbom/sbom.cdx.json` is a small illustrative CycloneDX file for demo/navigation purposes. For the live demonstration, prefer an SBOM freshly generated by your ASPM/CI integration.
